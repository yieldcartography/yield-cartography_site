# yc-alerts — one-time setup runbook

Per-user email alerts for yieldcartography.com: registration with magic
links, self-set thresholds, evaluated once a day when update_daily pushes
the fresh LW-NSS metrics. Everything below is one-time; afterwards the
system runs itself.

## 1. Resend (email sending)

We already have a Resend account (used for FinAcademy.ai) — reuse it:

1. In that account, Domains -> Add domain -> yieldcartography.com, and add
   the DNS records it shows (SPF TXT + DKIM CNAMEs) in the Cloudflare DNS
   panel for the YC zone. Wait for "verified". Alerts must send from
   alerts@yieldcartography.com, not from the FinAcademy domain, for
   deliverability and brand separation.
2. Create a SEPARATE API key for yc-alerts (per-project keys let you revoke
   one without touching FinAcademy). Keep it for step 3.
3. Mind the plan limits: the free tier's daily email quota is per ACCOUNT,
   shared with FinAcademy's sends. Fine at the start; if both grow, either
   upgrade the plan or move alerts to their own account.

## 2. Cloudflare Worker

From ~/Documents/YC_site/yc-alerts/ (needs node; first run will ask you to
log in to the Cloudflare account that owns the yieldcartography.com zone):

    npx wrangler d1 create yc_alerts
      -> paste the printed database_id into wrangler.toml
    npx wrangler kv namespace create SNAP
      -> paste the printed id into wrangler.toml
    npx wrangler d1 execute yc_alerts --file=schema.sql --remote
    npx wrangler secret put RESEND_KEY      (the key from step 1)
    npx wrangler secret put PUSH_SECRET     (long random string, e.g.
                                             `openssl rand -hex 32`)
    npx wrangler deploy

The route in wrangler.toml puts the API on
https://yieldcartography.com/api/* so the /alerts/ page calls it
same-origin. Nothing else on the site uses /api/, so no collision.

## 3. Pipeline side (the Mac)

Create ~/YIELDS/alerts_config.json:

    {"url": "https://yieldcartography.com/api/metrics",
     "secret": "<the same PUSH_SECRET value>"}

That's all: update_daily Step 13a6 (alerts_push.py) starts pushing on the
next run. Until the file exists the step is a silent no-op. First push
only stores the snapshot; alerts start from the second push.

## 4. Site page

dist/alerts/index.html is generated by ~/YIELDS/alerts_publish.py (public,
no beta gate, chrome cloned from /lt/ — rerun after chrome changes). The
footer of every page links to it ("Email alerts"). Deploy = the usual git
push of YC_site.

## 5. Verify end to end

1. Open /alerts/, register your own address, click the link in the mail,
   set "10y zero moves >= 1bp" (temporarily low), save.
2. Run: python3 ~/YIELDS/alerts_push.py  (stores snapshot #1)
3. Next trading day's update_daily (or a second manual run after a new
   fit) should deliver the alert. Then raise the threshold to a real one.

## Site-news announcements

Users can also tick, on the same settings page: new dashboards & tools,
new shorts & movies, research news. Those emails are sent when YOU run,
after shipping something:

    python3 ~/YIELDS/announce.py --kind tabs --title "New tab: realised vols" \
        --url /vols/ --blurb "One line on what it shows."

kind = tabs | shorts | research. The announcement id is derived from
kind+title, and each user receives a given announcement at most once, so
re-running is safe. Same config/secret as the metrics push.


## Seeing who registered

    python3 ~/YIELDS/alerts_admin.py          # roster in the terminal
    python3 ~/YIELDS/alerts_admin.py --csv    # writes alerts_users.csv

Shows email, name, status (pending / confirmed / unsubscribed), news flags
(T/S/R), rule count and emails received. Raw alternative: Cloudflare
dashboard -> D1 -> yc_alerts -> Console, or
`npx wrangler d1 execute yc_alerts --remote --command "SELECT ..."`.

## Operations notes

- Metrics catalog v1: z1, z2, z5, z10 (annual-comp zeros, %), s2s10, NBP
  reference rate. Extending = add the key in worker.js METRICS + compute it
  in alerts_push.py; redeploy worker (users see the new metric in the
  dropdown automatically).
- One email per user per metrics date max (sends table unique index), so
  re-running the pipeline the same day cannot spam.
- GDPR: double opt-in (confirmed_at), one-click unsubscribe in every mail,
  consent text on the page; users are deleted on request with
  `npx wrangler d1 execute yc_alerts --remote --command "DELETE FROM rules WHERE user_id=(SELECT id FROM users WHERE email='x@y'); DELETE FROM users WHERE email='x@y'"`.
- Logs: `npx wrangler tail` while a push runs shows evaluation/send counts.
- The magic-link token is the credential (kept in the manage URL). Fine at
  this scale; if the audience grows, switch to short-lived session tokens.
